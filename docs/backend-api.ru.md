# Rio backend: база данных, API и бизнес-логика

Этот документ — контракт для фронтенда и карта бэкенда. Реализация включает подбор, публикацию портфолио и оценки работ. Регистрация, оплата, бронирование и уведомления не входят в текущий контур.

## Быстрый запуск

```powershell
python app.py --init-db
python app.py --host 127.0.0.1 --port 8000
```

Если `python` не находится, используйте путь из `start.ps1`. База создаётся в `data/rio.sqlite3`, миграции накатываются автоматически, а каталог повторно импортируется только при изменении SHA-256 файла `data/contractors.csv`.

Полный машиночитаемый контракт: `GET /api/openapi.json` или файл `docs/openapi.json`. Основной base URL: `/api/v1`. Старые `/api/meta` и `/api/recommend` сохранены для совместимости с уже опубликованными версиями интерфейса.

## Архитектура

```text
Frontend
  -> HTTP + JSON (back/http.py)
  -> validation and recommendation rules (back/recommendations.py)
  -> repository (back/repository.py)
  -> SQLite (data/rio.sqlite3)
  <- normalized response or stable error envelope
```

- `app.py` — запуск сервера и обратная совместимость с прежними Python-функциями.
- `back/database.py` — миграции, проверка хеша источника, транзакционный импорт.
- `back/repository.py` — каталог, календарь, портфолио, оценки и ранжирование работ.
- `back/recommendations.py` — валидация, жёсткие фильтры, ранжирование, объяснения.
- `back/http.py` — REST-маршруты, CORS, лимиты тела, коды ошибок и request ID.
- `back/migrations/` — воспроизводимая схема, портфолио и индексы.

## Схема базы

`vendors` хранит одно значение на подрядчика. Списки вынесены в справочники и таблицы связей:

```text
vendors 1 ── * vendor_categories    * ── 1 categories
        1 ── * vendor_event_formats * ── 1 event_formats
        1 ── * vendor_languages     * ── 1 languages
        1 ── * vendor_busy_dates
        1 ── * portfolio_works 1 ── * work_media
                              1 ── * work_ratings

catalog_metadata     source hash, file, sync time, row count
schema_migrations    applied migration versions
```

Ключ подрядчика — строковый `vendors.id`. `price_from_kzt > 0`; булевы флаги ограничены `0/1`; `max_hours` либо `NULL`, либо больше нуля. Внешние ключи и каскадное удаление включаются на каждом соединении. Индексы покрывают город/цену, категории, форматы, языки и занятые даты.

CSV остаётся seed-источником и удобным форматом передачи датасета; runtime читает уже SQLite. Для изменения схемы добавляйте новый нумерованный SQL-файл, не редактируйте применённую миграцию на работающей среде.

## API для фронтенда

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/v1/health` | готовность API и БД |
| `GET` | `/api/v1/meta` | значения select-полей, даты, статистика, демо |
| `GET` | `/api/v1/vendors` | каталог с фильтрами и пагинацией |
| `GET` | `/api/v1/vendors/{id}` | полная карточка |
| `GET` | `/api/v1/vendors/{id}/availability` | доступность по дням |
| `GET` | `/api/v1/works` | общий топ опубликованных работ |
| `GET` | `/api/v1/vendors/{id}/works` | работы конкретного подрядчика |
| `POST` | `/api/v1/vendors/{id}/works` | публикация новой работы |
| `GET` | `/api/v1/works/{id}` | работа и последние отзывы |
| `POST` | `/api/v1/works/{id}/ratings` | новая или изменённая оценка клиента |
| `POST` | `/api/v1/recommendations` | подбор до трёх карточек |
| `GET` | `/api/openapi.json` | OpenAPI 3.1 |

Каталог принимает `city`, `category`, `event_format`, `language`, `available_on`, `budget_lte`, `limit` (1–100) и `offset`. Пример:

```text
GET /api/v1/vendors?city=Алматы&category=Ведущий&available_on=2026-10-04&budget_lte=1500000&limit=20
```

Календарь принимает `from` и `to` внутри 23.09.2026–31.12.2026. Без них возвращается всё окно.

Запрос рекомендации:

```json
{
  "city": "Алматы",
  "date": "2026-10-04",
  "event_format": "корпоратив",
  "category": "Ведущий",
  "budget": 1500000,
  "hours": 4,
  "language": "русский",
  "preferences": "интеллигентный юмор импровизация"
}
```

`language`, `hours` и `preferences` опциональны. Enum-значения фронтенд должен брать из `/api/v1/meta`, а не хранить копию. Результат всегда различает `matched`, `no_category` и `no_match`. Пустой подбор — успешный HTTP 200, а не ошибка.

### Портфолио и оценки

Подрядчик публикует работу через `POST /api/v1/vendors/{vendor_id}/works`:

```json
{
  "title": "Оформление осеннего корпоратива",
  "description": "Сцена, фотозона и флористика на 180 гостей.",
  "event_format": "корпоратив",
  "city": "Алматы",
  "occurred_on": "2026-09-10",
  "media_urls": ["https://cdn.example.kz/rio/work-1.jpg"]
}
```

Разрешено до 10 HTTP(S)-ссылок. Клиент оценивает работу через `POST /api/v1/works/{work_id}/ratings`:

```json
{
  "client_id": "client_7fd19a",
  "client_name": "Алия",
  "score": 5,
  "comment": "Всё совпало с концепцией и было готово вовремя."
}
```

Пара `(work_id, client_id)` уникальна: повторный запрос меняет существующую оценку, а не накручивает счётчик. Топ сортируется по байесовскому рейтингу, затем по средней оценке, числу оценок, времени публикации и ID. Байесовская формула использует пять условных голосов со средней оценкой каталога, поэтому одна случайная «5» не обгоняет автоматически работу с большим числом устойчиво высоких оценок. Работа без оценок получает `ranking_score = 0`.

Рекомендованные карточки содержат `top_works` (до трёх) и `published_work_count`. Жёсткие условия подбора подрядчика не меняются из-за портфолио: рейтинг определяет порядок работ внутри портфолио, а не позволяет занятому или слишком дорогому подрядчику пройти фильтр.

Сейчас это API уровня MVP без аккаунтов: `vendor_id` и `client_id` являются идентификаторами вызывающей стороны, но не доказательством личности. Перед публичной записью эти два POST-маршрута нужно закрыть авторизацией или доверенным API gateway.

Все ошибки имеют один вид:

```json
{
  "error": "Человекочитаемое сообщение",
  "code": "validation_error",
  "request_id": "7c2c9bd9ad3e4ae1"
}
```

Основные HTTP-коды: `400` для query/JSON, `404` для неизвестного ресурса, `413` для тела больше 16 КБ, `415` для неверного Content-Type, `422` для бизнес-валидации. `X-Request-Id` возвращается и заголовком, и в JSON API-ответов.

Для фронтенда на Vite/React dev server разрешены origin `localhost` и `127.0.0.1` на портах 3000 и 5173. Другие origin задаются через переменную `RIO_CORS_ORIGINS`, список через запятую. URL базы можно переопределить через `RIO_DB_PATH` или `--db`.

Локальный `web/` использует `/api/v1`. При отдельном домене API до загрузки `app.js` задайте `window.RIO_API_BASE = 'https://api.example.kz/api/v1'` и добавьте origin сайта в `RIO_CORS_ORIGINS`.

## Бизнес-логика рекомендации

1. Валидируются обязательные поля, календарное окно, положительные бюджет/часы, известные формат и язык, длина пожеланий до 1000 символов.
2. Формируется исходный пул по точному городу и наличию категории.
3. Из пула исключаются занятые на дату, дороже бюджета, не работающие с форматом/языком и не покрывающие длительность. `max_hours = NULL` означает, что услуга не зависит от присутствия по часам.
4. Пожелания нормализуются: нижний регистр, `ё → е`, стоп-слова, первые шесть букв. Совпадения взвешиваются по редкости в каталоге.
5. Сортировка детерминирована: текстовый балл по убыванию, цена по возрастанию, затем ID. Возвращаются первые три.
6. Для карточки строятся проверяемое объяснение и цитата из исходного описания. Для исключённых профилей возвращаются все причины; счётчики могут пересекаться.

Жёсткие условия никогда не ослабляются автоматически. Тот же снимок базы и тот же JSON дают тот же порядок.

## Рекомендации фронтенду

- На старте один раз загрузить `/api/v1/meta` и выставить ограничения календаря.
- Отменять предыдущий запрос или игнорировать устаревший ответ при быстром изменении фильтров.
- Показывать `message` и `status`, не вычислять бизнес-состояние по длине `cards`.
- Для аудита использовать `rejected` и `exclusion_counts`; один подрядчик может иметь несколько причин.
- Не считать `price_from_kzt` окончательной сметой и явно подписывать цену «от».
- В логах ошибки сохранять `request_id`; внутренний текст исключения сервер наружу не отдаёт.

## Проверка

```powershell
python -m unittest discover -s tests -v
```

Тесты проверяют исходный алгоритм, ограничения на всех датах/категориях, детерминизм, синхронизацию SQLite, сохранность портфолио при синхронизации каталога, обновление оценок без дублей, рейтинг работ и реальные HTTP-контракты.
